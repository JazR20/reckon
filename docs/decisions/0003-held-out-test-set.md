# ADR 0003: a held out test split, executed once

**Status:** accepted
**Date:** 2026-08-22

## Context

Reckon generates its own corpus, which is the only way to have ground truth and therefore
the only way to measure precision at all. It also creates an obvious hazard: the same
person writes the data, the matcher and the scoreboard.

If tuning happens against the same batch the results are reported on, the published
numbers measure how well the matcher was fitted to one specific batch. That is not a
measurement of the system. It is a measurement of the fitting.

The track brief says one cherry picked match proves nothing. A whole batch tuned against
is the same failure at scale.

## Decision

Two seeds, two splits, generated on day one.

- **dev** is used for all development, tuning, prompt iteration and threshold selection.
- **test** is generated at the same time and not inspected. It is executed exactly once,
  at the end, and its result is the headline number in the README.

If the dev and test results diverge, the gap is published as a finding.

## Rationale

The gap between a dev number and a held out number is the single most informative
statistic about whether a system generalises. Reporting it costs nothing when the system
is sound and is the honest outcome when it is not.

There is also a practical point. Knowing the test set exists and cannot be touched
changes how thresholds get chosen. It removes the temptation to nudge a gate until the
scoreboard looks better, because the scoreboard that matters has not been seen.

## Alternatives rejected

**One split.** Simplest, and it makes the headline number meaningless.

**Cross validation.** Statistically stronger for a small corpus, and it multiplies model
cost by the number of folds while adding a layer of explanation that obscures the point.
The corpus is generated and can be made arbitrarily large, so the reason to use cross
validation does not apply.

**Generate test at the end.** Tempting, and wrong. A test split generated after the
matcher is finished is generated by a person who now knows what the matcher struggles
with, and the generator parameters would drift toward what already works.

## Consequences

- `eval/fixtures/test/` is committed but is not read during development. `CLAUDE.md`
  carries this as a hard rule.
- `npm run eval:test` is a separate command with an explicit `--once` flag, so running it
  is a deliberate act and appears in the shell history.
- If the test result is worse than the dev result, that is what gets published. The
  README states both.
