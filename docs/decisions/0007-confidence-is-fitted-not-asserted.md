# ADR 0007: confidence is fitted, not asserted

**Status:** accepted
**Date:** 2026-08-23

## Context

Every decision this system publishes carries a confidence. A human reading the report will
act on that number: a row at 0.95 gets a glance, a row at 0.55 gets checked. So the number
has to mean what it says.

The first version was a hand written formula. Start from a base set by how the settlement
was identified, subtract for perturbation, subtract for the propagation round, subtract
again if no settlement row was available. Every term was defensible in isolation.

Measured against outcomes it was badly wrong:

```
stated 0.21   observed 0.87   n=15
stated 0.53   observed 1.00   n=7
stated 0.66   observed 0.65   n=20
stated 0.73   observed 0.50   n=2
stated 0.81   observed 0.86   n=29
stated 0.95   observed 0.94   n=16
expected calibration error: 0.176
```

The top bucket was fine. The bottom two were not merely imprecise, they were inverted: the
system was least sure about rows it was getting right almost nine times in ten.

A confidence that does not track reality is worse than no confidence, because it is
actionable and wrong. It would send a reviewer to the rows that least need them.

## Decision

Confidence is the measured precision of rows carrying the same evidence.

Rows are bucketed by three features that were chosen because they were measured to matter,
not because they sounded relevant:

- **perturbation**, capped at 3, the dominant term
- **settlement row present**, whether the gross could be pinned exactly
- **first round**, whether the row committed immediately or only after contests resolved

The table lives in `src/match/calibration.json`, is regenerated by `npm run fit`, and is
committed so a reviewer sees exactly what the shipped system believes.

**Fitted on dev, never on test.** The test split is generated on day one, never inspected,
and run once at the end. If the fit does not generalise, the test result says so and that
gap is what gets published. See ADR 0003.

**Fitted from an UNGATED run.** The gate admits rows by confidence, and confidence is the
measured precision of those rows. Fitting from a gated run would measure the gate's own
output and the two would chase each other. So `npm run fit` opens the gate fully, scores
every candidate the solver produces, and the table describes the solver rather than the
gate applied to it.

Result: **ECE 0.176 to 0.053.**

## Small buckets

Laplace smoothing, `(correct + 1) / (n + 2)`.

A first version fell back to the pooled rate below eight observations. That replaced a
measured 0.60 with a pooled 0.82 and made calibration worse in exactly the buckets that
most needed honesty. Smoothing shrinks a small bucket toward 0.5 on its own, which is the
conservative direction, and it does so smoothly rather than at a cliff.

## The gate

The operating point is `confidence >= 0.85`, chosen from the published curve rather than
from taste:

```
conf >=   matched   precision   coverage
0.80           63       90.5%      15.8%
0.85           29       96.6%       7.3%
0.90           19       94.7%       4.8%
```

The two errors are not symmetric. A wrong auto match in reconciliation closes the book on
money that never arrived and nobody looks again. A review costs a person a minute. So the
gate is not set at the midpoint, and coverage is deliberately low, with the residue handed
to review where a human or a later tier can work on it.

## Alternatives rejected

**Keep the formula and tune it.** Tuning a formula against outcomes is fitting a model
badly, by hand, without a held out set. If the output is going to be fitted, fit it
properly and say so.

**A learned model over more features.** More features than 89 observations can support.
Three features and Laplace smoothing is the honest size of model for this much data, and
the corpus can be enlarged later if more is wanted.

**Report no confidence at all.** Defensible, and it makes the review pile unorderable. A
reviewer with 272 rows needs to know which to open first.

## Consequences

- `npm run fit` must be re-run whenever the matcher changes, or the table describes a
  system that no longer exists. The published ECE is the check on that.
- The table is fitted on dev's distribution. The large split is denser and more ambiguous,
  so its calibration is a genuine generalisation test and any gap there is reported.
