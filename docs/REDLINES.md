# Redlines

Rules this repository holds itself to. They exist because the domain is payments, and in
payments a leak is not an embarrassment, it is a legal and financial event.

## What never appears in this repository

1. **Credentials.** No API keys, tokens, secrets or `.env` values. `.env.local` is
   gitignored. `.env.example` carries key names and empty values only.
2. **Live money identifiers.** No real payment ids, order ids, settlement ids or bank
   reference numbers. These are not secrets in a cryptographic sense, but they correlate
   to real money movement for anyone who reads them.
3. **Customer data.** No names, emails, phone numbers, addresses or government
   identifiers belonging to any real person.
4. **Regulated fields.** Nothing in PCI scope, no card numbers or CVVs. Nothing in RBI
   scope, no KYC documents.

## What never enters a model prompt

The same four categories, plus the working rule that produced them:

> Synthetic data in the prompt. Real lookup off channel.

If a real record must be investigated, the prompt refers to it by a synthetic handle and
the real value is resolved outside the model context. This applies to development
sessions on this repository as much as it applies to the shipped pipeline.

## How the corpus is produced

Every record in `eval/fixtures/` is generated by `eval/generator/` from a committed seed.
Nothing is sampled from, derived from, or anonymised out of any real dataset. Names,
amounts, references and narration strings are synthesised.

The reason is not only privacy. Ground truth is required to measure precision at all, and
only generated data has ground truth that is known rather than assumed.

## Where the schemas come from

Field names, types and response shapes are derived from the public API reference and, for
some resources, from live **test mode** API responses captured with a test key. Test mode
responses contain no real money and no real customer. The provenance of every field is
recorded in `SCHEMA-PROVENANCE.md`.

The captured responses are used to shape the generator. They are not committed as
fixtures.

## Two incidents referenced in the design

`DESIGN.md` cites two real operational incidents at a business the author operates. Both
are described in terms of failure class, sequence and magnitude of error. Neither names a
customer, quotes an amount attributable to a customer, or reproduces any record. They are
in the document because a design decision that comes from a real failure is worth more
than one that comes from a guess, and because the failure class matters while the
customer does not.
